# PRD：Chat with Document

Status: ready-for-agent

> 術語以 `CONTEXT.md` 為準。數值類的規則（Context Budget、切塊大小、前幾名的數量等）以 `AGENTS.md` 為準，因為它是唯一的事實來源；本文件若與它不一致，以 `AGENTS.md` 為準。

## Problem Statement

使用者手上有一份很長的 PDF，例如一篇研究論文，想直接用提問的方式理解內容。他們的需求有三種：

- 想要一份涵蓋全文的摘要。
- 想要比較散落在不同章節裡的論點。
- 想要查表格裡的精確數字。

但 LLM 每次呼叫只能處理 10K tokens（題目的設定），整份文件放不進去。另外，使用者必須能確認答案真的來自文件，而不是模型憑記憶補充或自行編造。

負責評審的面試官還要在 demo 中親眼看到三件事：系統怎麼守住 10K 的限制、怎麼處理摘要，以及答案的根據在哪裡。

## Solution

一個在本機執行的網站，使用流程如下：

1. 使用者上傳一份 PDF。系統在背景處理，處理期間即時顯示進度；完成後顯示「文件概覽」（Document Summary），並開放提問。
2. 使用者提問後，系統先判斷 Question Type，再依類型走不同的回答路徑：
   - **Global**：從 Summary Tree 中挑出「放得進額度的最詳細那一層」，據此產生回答。
   - **Synthesis**：把問題拆成 Sub-queries，分別檢索後合併。
   - **Lookup**：精準檢索，並把表格和解讀它的段落一起帶出來。
3. 回答會逐字串流出來。每個論點都附 Citation，以頁邊旁註的形式顯示，點下去就能看到原文。文件裡沒有答案時，系統會明確回答「文件中未提及」。
4. Trace 面板會列出：判斷出的 Question Type、Standalone Question、檢索到的 Chunk，以及每一次 LLM 呼叫用了多少 token（以 10K 為滿格的長條）。所有 LLM 呼叫都不會超過 Context Budget。
5. 出錯時誠實呈現：截斷、無效的引用、連線失敗，各有明確的畫面狀態，不會把半截或沒有根據的答案當成正常結果。

## User Stories

1. 作為使用者，我想上傳一份 PDF，以便針對它的內容提問。
2. 作為使用者，我想在上傳後立刻看到處理進度（解析 → 切塊 → embedding → 摘要 n/N → 完成），以便知道系統在做什麼、還要等多久。
3. 作為使用者，我想在處理完成時馬上看到文件概覽，以便在提問前確認系統讀懂了什麼。
4. 作為使用者，我想在處理完成之前，提問框是停用的，並看到原因，以便不會送出得不到回答的問題。
5. 作為使用者，我想在上傳掃描檔（沒有文字層）時，立刻看到明確的錯誤訊息，以便知道系統不支援這種檔案，而不是等很久後才得到空洞的回答。
6. 作為使用者，我想重新上傳同一份檔案時不必再等待處理，以便快速回到對話。
7. 作為使用者，我想問「Summary this document.」就得到涵蓋全文的摘要（動機、方法、實驗結果、結論），以便快速掌握整份文件。
8. 作為使用者，我想用不同的格式或語言要求摘要，例如「用三句話、中文總結」，以便得到符合需求的摘要。
9. 作為使用者，我想問比較題，例如「Compare LightRAG with GraphRAG」，並得到涵蓋多個面向的比較，包括檢索方式、成本、增量更新和實驗勝率，以便不必自己翻遍各章節。
10. 作為使用者，我想問「有什麼限制」這類需要跨 Section 彙整、但不是比較的問題，並得到完整的回答，以便了解散落在各處的資訊。
11. 作為使用者，我想查表格裡的精確數字，例如「Performance of ablated versions of LightRAG」，並得到正確的數值，以便直接引用。
12. 作為使用者，我想在回答引用表格時，先看到數字的比較基準（例如「每格是 NaiveRAG 勝率 / 變體勝率」），以便正確解讀數字。
13. 作為使用者，我想讓回答點出表格中的反直覺結果，而不是籠統地說「完整版最好」，以便得到忠於數據的結論。
14. 作為使用者，我想讓每個論點都附上 Citation，以便確認答案的根據。
15. 作為使用者，我想在頁邊看到 Citation 的旁註（頁碼與 Section），以便邊讀回答邊看出處。
16. 作為使用者，我想點一下 Citation 就看到原文的 Chunk，以便親自核對。
17. 作為使用者，我想點摘要類回答的 Citation 時，看到該 Section 的頁碼範圍和摘要，以便知道這段摘要涵蓋原文的哪裡。
18. 作為使用者，我想讓找不到有效來源的句子被標成 Unverified，以便知道哪些內容沒有根據。
19. 作為使用者，我想在問到文件沒寫的事時，得到「文件中未提及」，以便不會被模型自行補充的內容誤導。
20. 作為使用者，我想用中文問英文文件，並得到中文回答，而且引用的數字保持原樣，以便用母語閱讀。
21. 作為使用者，我想追問（例如「那 GraphRAG 呢？」）時，系統能理解前文，以便自然地對話。
22. 作為使用者，我想讓回答邊產生邊顯示，以便不必對著空白畫面等待。
23. 作為使用者，我想在等待時看到目前的階段（判斷問題類型 → 檢索 → 思考中），以便知道系統還在運作。
24. 作為使用者，我想讓串流中的文字明顯標示為「暫定」，完成後才定稿，以便知道哪些內容還可能改變。
25. 作為使用者，我想在回答被截斷時，系統自動重試並顯示「重新產生中」，以便不必自己重新提問。
26. 作為使用者，我想在重試仍然失敗時看到錯誤訊息，而不是半截的答案，以便知道要換個方式提問。
27. 作為使用者，我想在連線失敗時看到錯誤訊息和重試按鈕，以便一鍵重試。
28. 作為使用者，我想在問題太長時被明確拒絕並得知原因，以便縮短問題後再問。
29. 作為使用者，我想在回答引用了「結構未能可靠重建」的表格時，看到這個限制的說明，以便對那些數字保持警覺。
30. 作為使用者，我想在對話時仍然能看到文件概覽，以便隨時回顧全文脈絡。
31. 作為評審，我想在 Trace 看到 Question Type、Standalone Question 和 Sub-queries，以便理解系統如何規劃每個問題。
32. 作為評審，我想看到每次 LLM 呼叫的 token 用量，並以 10K 為滿格的長條呈現，以便確認 Context Budget 確實守住了。
33. 作為評審，我想看到每次呼叫的 think 等級和輸出預留，以便理解思考過程如何計入額度。
34. 作為評審，我想同時看到系統估算的 token 數，和模型回報的 `prompt_eval_count`，以便確認估算是保守的。
35. 作為評審，我想展開模型的思考內容（預設收合），以便了解它怎麼推理。
36. 作為評審，我想看到檢索到的 Chunk 和它們的相似度分數，以便評估檢索品質。
37. 作為評審，我想只安裝 Python 就能在本機啟動整個網站，以便不必處理前端的建置工具。
38. 作為評審，我想上傳自己的文件（包括中文文件），系統一樣能處理，以便確認系統不是只針對 LightRAG 論文調校過。
39. 作為評審，我想看到長文件的 Group Summary 確實運作，以便確認摘要機制能擴展到超過 10K 的文件。
40. 作為評審，我想看到 eval 報告（Q1～Q3 的通過率、每次呼叫的 token 用量與延遲），以便用數據評估品質。
41. 作為開發者，我想用一個指令跑確定性測試，而且不需要雲端 LLM，以便頻繁驗證。
42. 作為開發者，我想用一個指令跑回答評估，並在報告目錄產生 markdown 報告，以便比較不同設定。
43. 作為開發者，我想讓 eval 每題重複跑 N 次並計算通過率，以便看出 LLM 輸出的不穩定程度。
44. 作為開發者，我想為每條 Golden Fact 指定檢查方式（`contains` / `judge` / `forbidden`），以便正確檢查帶有前後文的數字和錯誤結論。
45. 作為開發者，我想在 budget guard 被觸發時立刻收到錯誤，以便發現上游沒有把內容安排進額度的 bug。
46. 作為開發者，我想在修改切塊或摘要規則後，舊的快取自動失效，以便不會測到過時的結果。
47. 作為開發者，我想透過設定調整 Chunk 大小、前幾名的數量和 think 等級，以便用 eval 比較不同設定。
48. 作為開發者，我想替換 LLM 或 Embedder 時只換一個 adapter，以便測試時改用假的 LLM，也方便日後更換模型。
49. 作為開發者，我想用一個腳本下載固定版本的測試文件，以便測試能夠重現。
50. 作為開發者，我想讓每一次 LLM 呼叫都留下紀錄（估算 tokens、實際 tokens、思考內容、延遲、`done_reason`），以便除錯與展示。

## Implementation Decisions

### 模型與依賴

- **LLM：** `gpt-oss:120b-cloud`，透過本機 Ollama daemon 的原生 chat API 呼叫，不需要 API key。只使用 `think` 的 `low` 和 `medium` 兩個等級；`high` 已確認會把 Q2 的回答擠掉，所以不用。
- **Embedder：** 本地 Ollama 的 `bge-m3`。
- **Tokenizer：** tiktoken `o200k_harmony`，再加上 300 tokens 的安全邊際（已實測：這個估算比實際偏多約 225，是保守的）。
- **不引入 RAG 框架。** 解析、切塊、檢索都用基礎函式庫自己實作。

### 模組

這些模組都是內部實作，對外只透過「上傳 Document」和「提問」兩個操作發揮作用。

1. **PDF Parser**
   - 輸入 PDF bytes，輸出結構化的 Document：Section 樹，底下是段落、表格和頁碼。
   - 抽不出文字層時，直接回報錯誤。
   - **章節標題：** 用字體大小的相對關係判斷。出現最多的字體大小視為內文，比內文大或是粗體的才是標題；編號和標題分在兩行時要合併。完全偵測不到標題時，用固定長度切出虛擬 Section。
   - 移除 References；附錄保留，並標示為 Appendix。
   - **表格：** 用文字座標重建無框線的表格，表頭要寫明每個數字的意義。重建失敗時，保留原始文字，並標記為「結構未能可靠重建」。不做 LLM 重排的備援。同時清除數學斜體留下的 `_` 等雜訊。
2. **Chunker**
   - 以 Section 為邊界；把整段段落裝進 Chunk，裝到約 500 tokens 就換下一塊，段落之間不重疊。
   - 只有單一段落過長時，才在句子邊界切開，並重疊約 10%。句子邊界同時支援中英文標點。
   - 表格成為 Table Chunk，並和內文中提到它的段落互相連結。超過 2,000 tokens 的表格依列分段，每段重複表頭。
   - 每個 Chunk 前面都加上 Section 標題，並帶有頁碼。
3. **Summary Tree Builder**
   - **Section Summary：** 長度約為原文的 15%，最短 80、最長 500 tokens；同時最多 4 個平行呼叫。
   - **Group Summary：** 只有在 Section Summary 加起來放不進額度時才建立，一層層往上合併。
   - **Document Summary：** 最頂層，作為文件概覽。
   - 每個節點都記錄來源：Section Summary 記錄它的全部 Chunk；Group Summary 記錄它涵蓋的 Section。
4. **Index**
   - 透過 Embedder 對「Section 標題 + Chunk 文字」做 embedding，用 cosine 相似度檢索。
   - 支援帶出相鄰的 Chunk，以及和 Table Chunk 互相連結的段落。
   - 一開始不使用 BM25，要不要加由 eval 決定。
5. **LLM Gateway**
   - 所有 LLM 呼叫的唯一入口。依「呼叫類型」查詢 think 等級、輸出預留和 prompt 上限。
   - 呼叫前先估算 token 數，超過額度就 raise。guard 一旦被觸發，就代表上游有 bug。
   - 支援串流，並把每次呼叫的估算值、`prompt_eval_count`、`eval_count`、思考內容、延遲和 `done_reason` 寫進 Trace。
6. **Router**
   - 一次 LLM 呼叫（`low`），以 JSON schema 輸出 Question Type、Standalone Question 和 Sub-queries。
   - Prompt 規定：不確定是 Lookup 還是 Synthesis 時，選 Synthesis。
   - JSON 壞掉時退回 Lookup；連線失敗時發出錯誤事件。
   - 對話歷史只帶最近 2 輪，每輪截到 500 tokens。
   - 問題本身超過 1,000 tokens 時，不呼叫 LLM，直接拒絕。
7. **Context Packer**
   - 依 Question Type 套用檢索規則：
     - Lookup：前 5 名，加上連結和相鄰的 Chunk。
     - Synthesis：Standalone Question 取前 3 名，每個 Sub-query 取前 2 名，合併後去除重複。
     - Global：使用 Summary Tree 中放得進額度的最詳細那一層。
   - Chunk 依原文順序排列，並標上 `[C#]`；Section Summary 標上 `[S#]`。
   - 內容超過約 6,000 tokens 時，改用分批抽取：每條抽出的事實都要保留 `[C#]`。抽出的事實仍然放不下時，再分批合併一次。
8. **Answer Generator**
   - `medium` 等級，輸出預留 3,000。
   - Prompt 規則：只根據提供的內容回答；用編號標示引用；引用表格時先說明比較基準；找不到答案時回答固定的一句話；用提問的語言回答，但數字保持原樣。
   - 只要 `done_reason=length` 就算失敗：改用 `low` 重試一次，再失敗就發出錯誤事件。
9. **Citation Validator**
   - 把編號轉成「頁碼 + Section」。
   - 遇到不存在的編號時，移除該編號，把那句話標成 Unverified，並把數量記進 Trace。
10. **Ingestion Jobs 與快取**
    - 上傳後立刻回應，在背景處理，並推送階段事件。
    - 快取的鍵值是「檔案內容的雜湊值 + 處理流程的版本」，存放 Chunk、embedding 和 Summary Tree。
    - 不快取回答。
11. **HTTP API**（FastAPI）
    - 提供的操作：上傳 Document、訂閱處理進度（SSE）、取得文件概覽、依編號查詢來源原文（Chunk 或 Section）、提問（SSE）。
    - 同時提供 build 好的前端。
12. **Frontend**（React + Vite + TypeScript）
    - 視覺採用 `tufte-dataink` recipe：
      - Citation 以頁邊旁註呈現，Trace 用以 10K 為滿格的迷你長條呈現 token 用量。
      - 暫定的文字要有明顯的樣式，思考內容可以收合。
      - 內文 15～16px，Noto Serif TC 字型檔放在 repo 裡，不加裝飾性動畫。
    - build 好的檔案一起 commit。
13. **Eval Harness**
    - Golden Facts 分成兩類：必須出現的事實，以及 forbidden claim。數字類的事實要寫明變體、資料集、指標和比較方向。
    - 三種檢查方式：
      - `contains`：只檢查專有名詞，比對前先統一寫法。
      - `judge`：必須逐字摘錄證據句，並驗證這句話確實出現在回答中。
      - `forbidden`：judge 只要能摘錄出這個錯誤結論，就判定失敗。
    - 報告寫成 markdown，支援每題跑 N 次。

### Context Budget（每次呼叫：prompt tokens + 輸出預留 ≤ 10,000）

| 呼叫類型 | think | 輸出預留 | prompt 上限 |
|---|---|---|---|
| Router | low | 600 | 9,100 |
| Section Summary | low | 1,200 | 8,500 |
| Group Summary | low | 2,500 | 7,200 |
| Document Summary | low | 2,500 | 7,200 |
| 分批抽取事實 | low | 1,000 | 8,700 |
| 產生回答 | medium | 3,000 | 6,700 |
| Judge（eval 用） | low | 1,000 | 8,700 |

### 事件契約（前後端共用；後端的模型就是事件格式的唯一來源，前端的 TypeScript 型別要與它對齊）

- **上傳：** 依序發出多個 `stage` 事件（含目前階段和進度），最後以 `ready`（附文件概覽）或 `error` 結束。
- **提問：** 事件依序如下，任何一步都可能改發 `error`：
  1. `plan`：Question Type、Standalone Question、Sub-queries。
  2. `retrieval`：檢索到的 Chunk，附相似度分數。
  3. `citation_map`：編號 → 頁碼與 Section 的對照表。
  4. `thinking`：模型的思考內容，可能沒有這個事件。
  5. `delta`：暫定的回答文字。
  6. `retry`：只有被截斷而重試時才會出現；收到後前端要清除原本的暫定文字。
  7. `final`：定稿的回答、驗證過的 Citation 和 Unverified 標記。
  8. `trace`：每次 LLM 呼叫的紀錄。

## Testing Decisions

- **Eval harness 的測試邊界（Main 2026-10-13 澄清）：** Golden Facts 評分器本身是獨立的驗收工具，可以透過其 `check_fact` 公開入口寫確定性測試，驗證逐字證據、數值關聯及 forbidden 規則。這不取代應用層的 upload／ask 驗證，也不擴大 Parser／Chunker／Index 內部單元測試範圍。

- **好的測試只檢查外部行為。** 測試透過兩個操作進行：「上傳 Document」和「提問」。斷言的對象是它們發出的事件和產生的 Document，也就是使用者在介面上會看到的東西。Parser、Chunker、Index 這些內部模組不另外寫單元測試，所以內部重構不會讓測試壞掉。
- **唯一的主要 seam 是應用層的這兩個操作。** LLM 和 Embedder 是可以替換的外部依賴：
  - **確定性測試**（一般的 pytest）：使用「照劇本回應、並記錄每次呼叫的假 LLM」，搭配真的本地 bge-m3（結果是固定的，但需要 Ollama 開著）。要驗證：
    - Table 2 重建後，每一格都正確。
    - 沒有 Chunk 跨越 Section；References 不在索引中；附錄有標示。
    - **假 LLM 記錄下來的每一次呼叫，都沒有超過 Context Budget。**
    - Q3 產生回答時的 prompt 裡有 Table 2，以及討論它的段落。
    - Q2 的 Sub-queries 能檢索到成本和增量更新的段落。
    - 回答被截斷時會重試，再失敗就發出 `error` 事件，而且不會發出 `final`。
    - 無效的引用會被標成 Unverified。
    - 超長的問題會被拒絕，而且完全沒有呼叫 LLM。
    - 掃描檔上傳時就回報錯誤。
    - 同一份檔案第二次處理時會使用快取。
    - Router 回傳壞掉的 JSON 時，會退回 Lookup。
  - **回答評估**（`-m eval`，使用真的 gpt-oss）：
    - Q1～Q3 的 Golden Facts，包括 forbidden claim。
    - Router 的 12 題回歸測試。
    - 文件中沒有答案的 3 題。
    - 第二份文件的 2～3 題。
- **HTTP / SSE 層**只寫 1～2 個契約測試：上傳後最後會收到 `ready`；提問時事件的順序正確。
- **前端**不寫單元測試。改用 web-design-engineer 的瀏覽器驗收來確認畫面，並用 TypeScript 型別對齊事件格式。
- **可以參考的既有做法**（目前還沒有正式的測試，但實測腳本已經示範了要怎麼做）：
  - Router 的 think 等級實測：12 題已標好答案的問題，可以直接轉成 router 的回歸測試。
  - 回答的 think 等級實測：示範了怎麼用真實大小的 context 呼叫模型，並檢查 Golden Facts。這次也學到，比對前要先統一連字號（gpt-oss 會輸出 U+2011），而且數字不能只靠字串比對。
  - Embedding 的 bake-off：示範了用「標記字串」判斷哪些 Chunk 算相關，再計算檢索排名。
- **調參實驗也透過 eval 進行：** Chunk 大小（例如 256 / 500 / 800）、前幾名的數量、是否加入 BM25，以及產生回答用 `low` 還是 `medium`。

## Out of Scope

- Docker、雲端部署、使用者登入、多使用者。
- 一次對話多份文件、Graph RAG（實體抽取建圖）。
- 掃描檔的 OCR；用 LLM 重排表格的備援。
- 對話歷史摘要（只把追問改寫成完整問題）；服務重啟後保留對話紀錄（對話只存在記憶體中）。
- 摘要逐句追溯來源（只追溯到 Section 層級）。
- 自動依剩餘額度選擇 think 等級；使用 `think=high`。
- 前端單元測試。
- 簡報製作（另外安排在 10/15～10/18）。
